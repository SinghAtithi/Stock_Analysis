## TASK 3 — Yahoo throttle resilience + stale-while-revalidate

- Per-host state (`yahooHosts` map keyed by query1/query2): cooldownUntil, consecutive failures,
  in-flight count, wait queue. At most 2 concurrent curl calls per host (`yahooSlot`).
- On 429 (HTTP status **or** "too many requests" body, incl. JSON error payloads): `failures++`,
  cooldown = `nextBackoff(failures−1)` = min(60s·2ⁿ, 15min) + 0–15s jitter; log
  `[yahoo] 429 host=query1 backoff=XXs`. Success resets failures. Other errors (timeout, parse)
  don't count as 429 failures.
- `curlRaw` now appends `\n%{http_code}` so 429 HTML bodies (which fail JSON.parse without a
  matching message) are still detected.
- Pure `nextBackoff(n)` exported from `web/src/lib/backoff.ts`; unit-tested standalone
  (n=0→60–75s, 1→120–135s, 2→240–255s, 3→480–495s, 4→900–915s [cap], 10/99→900–915s, n<0 clamps).
- SWR: `cacheGet` no longer deletes expired entries; `cacheGetStale(key, withinMs)` returns
  expired-but-recent entries. getChart: on total upstream failure returns `{...entry, stale: true}`
  within 6h; getTicker within 30min. Cache semantics unit-tested standalone (fresh hit, expired
  not-fresh, retained-in-map, 5h<6h ok, 7h>6h no, 20min<30min ticker ok, 45min no).
- `/api/chart` passes `stale`/`degraded` through automatically (`NextResponse.json(payload)` —
  no route change needed).
- Live observation: repeated 429s from both hosts; log showed 63s → 72s → 125s backoffs
  (60s·2ⁿ growth working); failures persist because the IP is blocked, not because of code.
